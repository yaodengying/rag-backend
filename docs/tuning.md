# 检索参数调优（top_k / 两路权重 / rerank / chunk）

> 一句话：`scripts/tune_retrieval.py` 用**确定性指标**扫参数，不调 LLM、可反复重跑；
> 结论是**现有默认值已经是测出来的最优**，但每一条现在都有数据支撑，不再是"感觉还行"。

结果原始数据：`eval/tuning.json`（首轮，饱和）、`eval/tuning-recall.json`、
`eval/tuning-rerank.json`、`eval/tuning-chunk.json`。

---

## 一、为什么不能"改一个值试一下"

参数是**耦合**的：`top_k` 放大后重排才有得挑；重排阈值提高又需要更大的 `top_k`；
`chunk_size` 一变，向量本身就得重算。一次只改一个值，改动之间互相掩盖，永远收敛不了。

所以脚本做三件事：

1. 每个维度**分开扫**，用同一套确定性指标打分（不用 LLM，因此可复现）；
2. `top_k` 不需要重新检索——RRF 只吃排名，切片后融合等价于用更小的 `top_k` 检索，
   于是一次 max-depth 召回 + 内存切片就能扫完整个网格；
3. `chunk_size` 必须换 collection（切分变了向量就得重算），临时集合
   `<collection>__tune_<size>_<overlap>`，跑完删除。

指标：

| 指标 | 含义 | 备注 |
|---|---|---|
| `hit@k` | 正确片段进入前 k 的比例 | 饱和时无区分度 |
| `mrr` | 正确片段名次的倒数（第 1 名 = 1.0） | **本项目最有区分度的指标** |
| `top1_cos` | 命中的第 1 条片段的余弦相似度均值 | 衡量"块越大越稀释" |

## 二、真实语料测不出东西（这是第一轮的关键发现）

首轮直接在项目语料上扫 `top_k 4..16 × 4 种权重`，**20 组全部 hit=1.0 / mrr=1.0**。

原因很硬：

- 语料只有 3 篇文档、15 个片段、4 条事实；
- **每条事实独占一页**，问题是"这一页写了什么"级别；
- 语料规模（15 块）与召回深度（4~16）同量级，`top_k` 根本不起作用。

在这种语料上"调参"，只是在给当前配置盖章。所以真实语料现在只做一件事：
**饱和检测**——全 1.0 就明确打印「现有语料无法区分参数」，避免下次又拿它当依据。

## 三、合成基准：两版才做出区分度

### 第一版（失败）：每条事实独占一种参数名

24 台设备，每台配一个**不同的**参数名（工作电压 / 待机功耗 / 防护等级 …）。结果：

```
合成语料：8 块，24 条事实
20 组参数全部 hit=1.0 mrr=1.0 top1_cos=0.529
```

因为正确段落是**唯一同时命中「型号 + 参数名」**的那条，向量与 BM25 都把它排第一。
它测的是"模型认不认得出主题"，不是参数差异。

### 第二版（有区分度）：同参数名、异型号的硬负样本

24 台设备 × 4 个**共同的**参数名（工作电压 / 防护等级 / 保修期限 / 校准间隔），
措辞几乎逐字相同，只有型号与数值不同 → 96 条互相干扰的段落，32 块（chunk 300）。

于是「XG-8805 的防护等级是多少？」的竞争者是另外 23 条同格式段落，
必须靠**型号这个稀疏 token** 才能把正确那条挑出来。这才是参数真正起作用的地方。

## 四、结果

### 4.1 召回深度 × 两路权重（`--stage recall`）

```
top_k  vector_weight  bm25_weight  hit     mrr     top1_cos
6      0.5            0.5          1.0     0.9792  0.5687   ← 现有配置
8      0.5            0.5          1.0     0.9792  0.5687   ← 现有配置
12     0.5            0.5          1.0     0.9792  0.5687
6      0.3            0.7          1.0     0.9792  0.5675
6      0.7            0.3          1.0     0.9583  0.5688
4      0.5            0.5          0.9583  0.9583  0.5687
4      0.3            0.7          1.0     0.9514  0.5682
2      0.5            0.5          0.9167  0.9167  0.5705
2      0.3            0.7          1.0     0.9375  0.5702
4..12  1.0            0.0          0.9583  0.8368  0.5707   ← 纯向量
```

三条结论，每条都有数：

1. **混合检索确实在干活**：纯向量 `mrr=0.8368`，混合 `0.9792`，差 **+0.14**——
   而且这个差距与 `top_k` 无关（纯向量在 4/6/8/12 上全是 0.8368），
   说明差距来自"BM25 能命中型号这种稀疏 token"，不是深度不够。这是混合检索第一次有硬证据。
2. **`top_k` 有下限**：2 → 0.9167、4 → 0.9375~0.9583、**≥6 才饱和到 0.9792**。
   现有 8 已在饱和区，往下调到 4 会实打实掉分。
3. **权重 0.5/0.5 与 0.3/0.7 同分**（0.9792），0.7/0.3 略低（0.9583）。
   现有 0.5/0.5 不用动——它已是最优档，且不比任何一档差。

### 4.2 重排条数 × logits 下限（`--stage rerank`）

```
rerank_k  min_score  hit     mrr     top1_cos
2..6      -10/0/2    1.0     0.9792  0.5681      ← 12 组完全并列
对照：不重排、按融合分截断 top4 → hit=1.0 mrr=0.9792
```

**12 组一模一样，且与"不重排"完全一致。** 这不是"重排没用"，而是**这个基准测不出重排的价值**：

- 基准里的问题都有唯一正确答案，且正确段落本来就排第 1，重排无事可做；
- 重排买到的是**上下文纯度**（把送进模型的 4 条压到 1 条）与**歧义查询下的纠偏**，
  这两件事都不体现在 hit/MRR 上。

已有的真实语料证据仍然成立，所以 `RERANK_TOP_N=4` / `RERANK_MIN_SCORE=0.0` 保持不变：

- 重排名次一条没改，但把每题上下文从 4 条压到 1 条（省 token、少干扰）；
- 歧义口语查询上重排会错排，且 `0.0` 是**硬过滤**：只共享「故障」一词的「保修范围」页
  被推第 1，相关页拿负分被整条丢弃 → 最坏情况是拒答一个有答案的问题。
  把阈值抬到 `2.0` 在首轮基准上已经开始掉分（hit 1.0 → 0.9583），方向不对。

### 4.3 切分块大小（`--stage chunk`）

```
chunk_size  overlap  chunks  avg_chars  hit  mrr     top1_cos
150         25       96      83.7       1.0  1.0     0.695
300         50       32      251.0      1.0  1.0     0.5681   ← 现有配置
500         83       24      334.7      1.0  0.8194  0.5251
```

- **500 明确要否掉**：`mrr` 从 1.0 掉到 0.8194。一块里塞进 4 条同参数段落，
  正确那句被稀释，融合后名次掉出前 4。这是"块越大越省钱"的代价第一次被量化。
- 150 与 300 的 `mrr` 相同，但 150 的块数是 3 倍（96 vs 32），
  且每块只有 83 字——上下文被切碎，模型拿到的是半句话，跨块的连贯论述会断。
  索引行数 ×3、引用条数 ×3，换不到任何指标收益。
- `top1_cos` 单调验证了稀释效应：0.695 → 0.5681 → 0.5251。

**结论：`CHUNK_SIZE=300 / CHUNK_OVERLAP=50` 保持。**

## 五、最终取值与依据

| 参数 | 取值 | 依据 |
|---|---|---|
| `RETRIEVE_TOP_K` | 8 | ≥6 饱和；4 掉到 0.9583、2 掉到 0.9167 |
| `HYBRID_VECTOR_WEIGHT` / `HYBRID_BM25_WEIGHT` | 0.5 / 0.5 | 最优档；纯向量仅 0.8368（+0.14 来自 BM25） |
| `HYBRID_RRF_K` | 60 | 原论文与业界通行值；本量级（8~50 条）下偏平滑属安全 |
| `RERANK_TOP_N` | 4 | 基准测不出差别；按"上下文纯度"定，5 条以上纯增 token |
| `RERANK_MIN_SCORE` | 0.0 | 2.0 已开始误杀真命中（真实语料证据更硬：歧义查询误伤） |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | 300 / 50 | 500 → mrr 0.8194；150 → 指标不变但块数 ×3、上下文被切碎 |
| `HYBRID_DENSE_MIN_SIMILARITY` | 0.0 | 混合模式下设阈值会静默清空整条稠密路（见 pipeline.md） |
| `HYBRID_BM25_MIN_SCORE` | 0.0 | 中文分析器不过滤停用词，分无界且随语料漂移；要设也得按实测分布设 |

**所以本次调优没有改任何 `.env` 值**——但"为什么是这些值"从推断变成了测量。

## 六、怎么复跑

```bash
cd <项目根目录>
set NO_PROXY=localhost,127.0.0.1,::1
.venv\Scripts\python.exe scripts/tune_retrieval.py                    # 三阶段全跑（约 8 分钟）
.venv\Scripts\python.exe scripts/tune_retrieval.py --stage recall     # 只扫召回（约 1.5 分钟）
.venv\Scripts\python.exe scripts/tune_retrieval.py --stage chunk --keep-temp
.venv\Scripts\python.exe scripts/tune_retrieval.py --out eval/tuning.json
```

需要 Milvus 已启动、BGE 权重就位（走 CPU）。临时 collection 默认跑完即删，
`--keep-temp` 可保留下来手动查。

**换模型 / 换语料后必须重跑**：`top_k` 的下限、权重的比值、块大小的拐点都依赖
embedding 模型与语料形态，这些数字不是普适常数。
